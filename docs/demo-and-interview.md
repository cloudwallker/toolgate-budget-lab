# 演示与面试说明

本项目展示跨 API 进程的工具调用预算和故障边界。本地 64 项测试及五场景演示已完成；展示时以实际生成的报告与原始记录为准，不使用预设吞吐数字。

## 运行演示

按 [README](../README.md) 安装依赖并启动 PostgreSQL，然后执行：

```bash
uv run python scripts/load_lab.py --requests 100
```

该命令使用独立测试数据库、临时端口、两个 API 子进程和一个独立模拟工具进程；不会使用开发账号额度。演示分为四组、五个场景：

| 组别 | 场景 | 展示证据 |
| --- | --- | --- |
| 正常调用 | `normal-paced` | 两个客户端并发，工具延迟 200ms；准入、终态和占位归零。 |
| 日额度竞争 | `daily-three-race` | 100 个请求争三份额度，工具屏障维持占位；仅三次新准入。 |
| 并发竞争 | `concurrency-two-race` | 100 个请求争两个名额；持位为二，其余拒绝，工具峰值不超二。 |
| 故障 | `terminal-response-lost`、`api-process-killed` | 工具已完成却丢响应，或工具运行中 API 被强杀；均先保留占位，取得原 operation 终态后释放一次。 |

前面三个场景各使用 `--requests` 指定数量；两个故障场景是固定的小型验证，不各自生成 100 个请求。工具挂起屏障保证争抢期间不会因快速完成而把后续请求正常准入误判为超发。

命令完成后查看 [负载报告](reports/load-report.md) 和 [原始 JSON](../artifacts/load-results.json)。重点核对：准入数与工具 started 数一致，日额度未退款，场景终态 inflight=0，以及故障场景 RELEASED 只有一条。被强杀请求没有可返回的 HTTP 响应，应单独计数，不能伪造成功或 202。

时间与峰值来自工具进程的单调时钟观测，数据库记录用于持久化状态核对；Docker 墙钟曾发生回拨，不能用异常墙钟区间证明峰值。最终报告已据此复跑。客户端 HTTP 延迟、预算提交确认耗时、principal 锁获取耗时和工具执行耗时分别报告。

## 3～5 分钟讲解脚本

**0:00～0:40，问题。**“两个 Agent 共享工具额度，单进程内存计数不能协调两个 API。另一个难点是超时：停止等待不能证明工具已经停止，所以立即释放并发名额可能让仍在执行的调用重叠。”

**0:40～1:30，准入。**展示 `principals`、`daily_usage`、`calls`。每个 principal 的行锁串行化检查与占位变更。在 READ COMMITTED 下，先取锁，再读取当日日额与所有日期的 held 调用；扣额、创建 reserved 和审计同一事务提交。并发数量从 held 记录派生，不另维护可能漂移的计数器。UTC 日期从数据库时钟读取，跨日旧调用仍占位。

**1:30～2:10，发送边界。**“reserved 通过状态条件更新取得 dispatching 发送权，必须确认事务提交后才发 HTTP。网络在事务外，避免慢工具长时间持有数据库锁。回收与发送权竞争同一锁和状态，回收赢了就不能发。提交确认丢失可能已经留下完整记录，当前执行者仍不发送。”展示同键重放：返回原调用状态，不再扣额或发送；异参冲突。

**2:10～3:20，故障证据。**展示 API 强杀或响应丢失场景：另一个 API 返回并发超限，工具日志仍显示 started。只读对账按原 operation UUID 查询；匹配的可信 succeeded/failed 才释放。404、running、超时、500、TTL 或 PID 消失均不能替代终态证据。并发对账的多次返回不等于多次释放，应核对数据库 RELEASED 审计只有一条。

**3:20～4:10，实验边界。**“并发、TCP 断开和强杀使用真实 PostgreSQL 与独立进程。服务端任务取消用可控 HTTP transport 测试；提交确认丢失是在真实提交后注入异常，不是制造真实数据库网络故障。UTC 切换用固定时间替身，不是真实午夜。”展示 [验收表](acceptance.md)，说明各证据支持什么性质。

**4:10～5:00，取舍。**“unknown 可能永久占位。这里优先维持安全性，接受可用性下降；没有可靠终态接口的第三方工具不能直接套用释放协议。principal 行锁也可能成为热点，所以报告实际锁获取与提交确认耗时。项目是固定 HTTP 工具的正确性实验，不宣称通用 MCP 网关、竞品漏洞或生产就绪。”

## 常见追问

| 问题 | 回答要点 |
| --- | --- |
| 为什么不用 Redis？ | 首版以 PostgreSQL 同一事务保存预算、调用和审计，减少跨存储一致性问题；不是证明 Redis 不适合。 |
| 为什么失败不退日额度？ | 日额度定义为唯一调用的成功准入次数，不是成功工具数或付费账单；避免未知状态和重试造成计数歧义。 |
| API 崩溃会不会重跑工具？ | 不会自动重发。已 dispatching 的调用只查原 operation；未确认发送也可能长期占位。 |
| 能否按超时强制释放？ | reserved 从未取得发送权时可 CAS 回收；取得发送权后必须有可靠终态，超时本身不足以释放。 |
| 是否保证整个系统 exactly-once？ | 不作该承诺。受控环境中每个准入只有一个发送权，工具自身有唯一 operation 记录；边界之外需重新分析。 |
| 测试通过是否等于生产可用？ | 不等于。本机实验没有覆盖公网部署、OAuth、任意工具、数据库恢复到旧备份或跨集群。远端结果以 GitHub Actions 为准。 |
